# 改写对照示例

每对示例只展示"改了什么"，不展示推理过程。

## 1. 模糊需求 → 可执行任务（clarity）

**原文**

```text
帮我看看这个报错
```

**改写**

```text
帮我定位这个报错的原因并给出修复方案：报错文本见下，相关代码在当前工作区内。先说明根因，再给最小改动，不要顺手重构。
```

## 2. 编码任务 → 结构化（structured）

**原文**

```text
给用户列表加个搜索
```

**改写**

```text
目标：在用户列表页增加按昵称与邮箱的搜索。
上下文：列表数据来自现有用户接口；前端已有列表组件，无搜索组件。
要求：
1. 只改列表页组件与其数据请求，不改接口契约；
2. 输入停止 300ms 后才发起请求；
3. 无结果时显示空状态，不显示加载态。
验收：输入关键字能筛出匹配用户；清空关键字恢复全量列表；断网时提示失败而不是空白。
```

## 3. 规格待定 → 细化（detail）

**原文**

```text
定时清理日志
```

**改写**

```text
写一个定时清理日志的任务：清理运行目录下超过保留天数的日志文件，保留最近一份归档。删除前先记录将被删除的文件清单，删除失败时保留原文件并输出失败原因。

待确认：保留天数取多少（默认 7 天）？
```

注意：天数写成待确认，而不是替用户拍一个数字。

## 4. 系统提示词 → 精简（brief）

**原文**

```text
你是一个非常有经验的助手，请你在回答用户问题的时候一定要保持专业、准确、负责，不要编造内容，如果不知道就说不知道，尽量用中文回答。
```

**改写**

```text
用中文回答；不确定就直说，不编造。
```

## 5. 保留全部事实

**原文**

```text
把 build 目录下 index.js 里那个 Math.round 改一下，v2.3.1 之后金额差 1 分
```

**改写**

```text
修改 build 目录下 index.js 中金额相关的 Math.round 逻辑：v2.3.1 起存在差 1 分的偏差。给出改动前后对比，不改其它文件。
```

路径、版本号、偏差量原样保留——这是改写质量最容易掉分的地方。

## 6. 不该改写的情况

**原文**

```text
请按以下格式输出 JSON：{"name": string, "age": number}；只输出 JSON，不要解释。
```

**处理**：已经完整、无歧义。直接告诉用户"这条可以直接用"，不要为了交差而重写。

## 常见失败模式

- **加了技术栈**：原文只说"做个页面"，改写里出现 React——删掉。
- **把示例当需求**：原文举例说明，改写把例子写成硬性要求——改回"例如"。
- **扩大了范围**：原文"修这个 bug"，改写顺手加"并补测试"——除非原文要求，否则删掉。
- **过度结构化**：一句话请求被改成四段——退回 clarity。
- **翻译了专有名词**：`build`、`index.js`、`Math.round` 被翻成中文——恢复原样。
- **把执行当改写**：用户说"帮我改好这个提示词然后开始做"，只交了一段提示词就停了——改写后继续把任务做完。
- **把评估当改写**：用户问"这样问行吗"，直接甩一版改写——先回答"行不行、哪里不行"。
